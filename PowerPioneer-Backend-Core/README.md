# PowerPioneer Backend Core

A Django REST Framework backend for an employee wellbeing platform. It is built on the schema in [DB-Schema.md](DB-Schema.md).

It provides:

- **CRUD APIs** for all 11 tables, with filtering, search, ordering and pagination.
- **Manager and buddy management** with validation rules and an audit trail.
- **Wellbeing scoring** calculated from rosters, attendance, leave and survey answers, with per-factor explanations and automatic interventions.
- **JWT authentication** using `djangorestframework-simplejwt`.
- **Swagger UI** for exploring and testing every endpoint, generated by `drf-spectacular`.
- **WebSocket chat** using Django Channels, with room chat, direct messages and a push notification channel.
- **Local SQLite** database.

## 1. Local setup

Requirements: Python 3.12 or newer (tested on 3.14).

```powershell
# Windows PowerShell
python -m venv .venv
```

## 3. Project layout

```
config/       settings, URLs, ASGI (HTTP + WebSocket routing)
common/       shared permissions, scoped-queryset mixin, timestamp base model
employees/    employee table (also the auth user), auth endpoints, manager/buddy logic
rostering/    shift_roster, leave_request, attendance
surveys/      question, question_option, employee_response
wellbeing/    employee_risk_snapshot, risk_prediction, risk_explanation, intervention,
              feature extraction (features.py), scoring rules (scoring.py), orchestration (services.py)
chat/         WebSocket consumers, JWT WebSocket auth middleware, push notifications
templates/    chat test client
tests/        API, business-logic and WebSocket tests
```

### How the schema maps to Django

- Table and column names match the schema exactly. For example, the `manager_employee` foreign key is stored in the `manager_employee_id` column.
- Every `uuid` primary key is generated with `uuid4`. Every `*_employee_id`, `question_id`, `option_id`, `prediction_id` and `risk_snapshot_id` column is a real foreign key.
- `absence_episode_id` is a plain UUID used to group the attendance rows of one absence. It has no table of its own.
- Varchar columns that hold codes use enumerated choices, which Swagger shows as enums. Examples are `shift_type`, `status`, `risk_band` and `action_type`.
- **`employee` is the authentication user model.** It adds four auth columns to the schema: `password`, `last_login`, `is_staff` and `is_superuser`. Employees log in with their email.

## 4. API overview

All endpoints are under `/api/` and require a JWT access token unless noted otherwise.

| POST | `/api/auth/token/verify/` | Checks whether a token is valid. |

| GET | `/api/auth/me/` | Returns the current employee. |
| POST | `/api/auth/change-password/` | Changes the current employee's password. |

Every resource below supports `GET` (list), `POST`, `GET {id}`, `PUT {id}`, `PATCH {id}` and `DELETE {id}`.

| Path | Table |
|------|-------|

### Access rules

- **Staff** (`is_staff`) can read and write everything.
- **Managers** can read and write the shifts, attendance and leave of their **direct reports**. They can also manage those reports' buddies.
- **Employees** can read their own records. They can raise their own leave requests and answer their own surveys.
- **Employee and question lists.** Any authenticated user can read the employee directory and the question master data. Questions generated for one employee are visible only to that employee and to staff.
- **Calculated tables.** Snapshots, predictions and explanations are written by the calculator. Only staff can edit them directly.

## 5. Manager and buddy rules

The rules live in `employees/services.py`. Every change is also written to the `intervention` table as an audit record, with `action_type` set to one of `ASSIGN_MANAGER`, `REMOVE_MANAGER`, `ASSIGN_BUDDY` or `REMOVE_BUDDY`.

**Manager rules:**
- An employee cannot be their own manager.
- Both people must be active.
- **No cycles.** The new manager cannot sit anywhere below the employee in the reporting chain.
- The manager cannot also be the employee's buddy.

**Buddy rules:**
- An employee cannot be their own buddy.
- Both people must be active.
- A buddy is a peer. It cannot be the employee's manager or one of their direct reports.
- A buddy supports at most `BUDDY_MAX_ASSIGNEES` active employees. The default is 3, set by an environment variable.

**Buddy suggestions** rank active peers with spare capacity. People whose latest wellbeing band is HIGH or CRITICAL are excluded. The ranking adds:

| Factor | Points |
|--------|--------|
| Same department | +3 |
| Same location | +2 |
| Same job role | +1 |
| At least one year of tenure | +1 |
| Good latest wellbeing score | Up to +2 |
| Each person already supported | −0.5 |

**Deactivating an employee** moves their direct reports up to the leaver's own manager. It also removes them as a buddy from everyone they were supporting.

You can also set `manager_employee_id` and `buddy_employee_id` on `POST /api/employees/` or `PATCH /api/employees/`. Those changes go through the same rules.

## 6. Wellbeing score

`POST /api/wellbeing/calculate/` with `{"employee_id": "...", "snapshot_date": "2026-11-17"}` runs four steps:

1. **Feature extraction** (`wellbeing/features.py`) fills every column of `employee_risk_snapshot` from the source tables, for windows that end on the snapshot date:
   - **Hours** come from `shift_roster` over 30 days: contracted hours (weekly × 30/7), hours worked (actual, falling back to planned), and overtime as hours and as a ratio.
   - **Shift patterns** come from `shift_roster` over 30 days:
     - Night shifts are `NIGHT` shifts or shifts with 3 or more hours between 23:00 and 06:00.
     - Long shifts are 12 hours or longer.
     - The longest runs of working days and of nights, and the shortest rest between shifts.
     - Counts of short-notice changes and missed breaks.
     - The understaffed ratio and the average patient-load ratio.
   - **Redeployments** come from `shift_roster` over 90 days.
   - **Absences** come from `attendance` over 90 days. Only unplanned absences count, meaning `SICK`, `UNPLANNED`, `UNAUTHORISED` or `FAMILY_EMERGENCY`. Days are counted, and episodes are grouped by `absence_episode_id` or by consecutive dates.
   - **Late arrivals** come from `attendance` over 30 days.
   - **Leave** comes from `leave_request`. It gives the days since the last approved non-sick break of 5 or more days, falling back to the hire date. It also counts cancelled or rejected requests over 90 days.
   - **Maternity return** metrics are tracked for the first year back. They cover overtime since return, the variance between planned and actual hours, how often agreed adjustments were honoured (no nights, no long shifts, no short-notice changes), and missed nursing or recovery breaks.
   - **Survey sentiment** uses `employee_response` answers from the last 30 days. Each answer is normalised to 0–1 against the min and max `normalized_score` of its question's options.
2. **Scoring** (`wellbeing/scoring.py`) starts at 100 and subtracts capped penalty points, one rule per risk factor. Unplanned absence is scored with the Bradford factor, which is episodes² × days. Survey sentiment then adds between −10 and +10. The result is clamped to 0–100, where higher is better.

   | Wellbeing score | Risk band |
   |-----------------|-----------|
   | 75 or more | LOW |
   | 55 to 74 | MODERATE |
   | 35 to 54 | HIGH |
   | Below 35 | CRITICAL |

3. **Persistence.** The snapshot is upserted per employee and date, storing `wellbeing_score` and `risk_label`. A `risk_prediction` row stores `risk_score = 100 − wellbeing`, the band and the model `wellbeing-rules` version `1.0.0`. One `risk_explanation` row is stored per contributing factor:
   - `shap_value` holds the points that factor added or removed. The score is additive, so these values sum to the total.
   - `contribution_direction` is `INCREASES_RISK` or `DECREASES_RISK`.
4. **Interventions** are raised only for **HIGH** and **CRITICAL** results:
   - `NOTIFY_MANAGER` goes to the manager. If there is no manager, it is recorded as `FAILED`.
   - `SCHEDULE_CHECKIN` is added for CRITICAL results.
   - `NOTIFY_BUDDY` goes to the buddy. If there is no buddy, `SUGGEST_BUDDY` is created with the top 3 suggestions instead.

   Pending interventions of the same type are not duplicated within 7 days. Recipients connected to `/ws/notifications/` get a real-time push.

All thresholds, weights and caps are plain constants at the top of `features.py` and `scoring.py`. The structure lets a trained model replace the rules later, using `is_training_record` and `risk_outcome_within_30d` as the training data.

Scheduled recalculation, for example nightly via cron or Task Scheduler:

```bash
python manage.py calculate_wellbeing                     # all active employees, today
python manage.py calculate_wellbeing --date 2026-11-01 --employee <uuid> --no-interventions
```

## 7. WebSocket chat

Browsers cannot set headers on a WebSocket, so the JWT access token goes in the query string. Non-browser clients can send an `Authorization: Bearer` header instead.

| Endpoint | Purpose |
|----------|---------|
| `ws://127.0.0.1:8000/ws/chat/<room>/?token=<access>` | Group room. Any authenticated employee can join. Room names use `A-Z a-z 0-9 _ -`. |
| `ws://127.0.0.1:8000/ws/chat/direct/<employee_id>/?token=<access>` | One-to-one chat between a manager and a report, or between buddies. Staff can message anyone. |
| `ws://127.0.0.1:8000/ws/notifications/?token=<access>` | Receive-only pushes for interventions and new direct messages. |

Frames the client sends:

```json
{"type": "message", "message": "Hello team"}
{"type": "typing"}
```

Frames the server sends:

```json
{"type": "message", "room": "ward-1", "message": "Hello team",
 "sender": {"employee_id": "...", "full_name": "...", "email": "..."}, "timestamp": "2026-11-17T10:00:00+00:00"}
{"type": "join" | "leave" | "typing", "room": "ward-1", "sender": {...}}
{"type": "notification", "kind": "direct_message" | "intervention", ...}
{"type": "error", "error": "..."}
```

| Close code | Meaning |
|------------|---------|
| 4001 | Missing or invalid token |
| 4003 | Direct chat is not allowed between these two people |
| 4004 | Employee not found |

The quickest way to try it is to open `/chat/test/` in two browser windows. Log in as two different demo users and connect to the same room. You can also connect from the command line:

```bash
npx wscat -c "ws://127.0.0.1:8000/ws/chat/general/?token=<access>"
```

Messages are relayed live and **not stored**, because the schema has no chat table. The in-memory channel layer works for a single server process. For several processes, switch `CHANNEL_LAYERS` to `channels_redis`.

## 8. Configuration

| Environment variable | Default | Purpose |
|----------------------|---------|---------|
| `DJANGO_SECRET_KEY` | Development key | Set a real secret outside local development. |
| `DJANGO_DEBUG` | `True` | |
| `DJANGO_ALLOWED_HOSTS` | `*` | Comma-separated list. |
| `BUDDY_MAX_ASSIGNEES` | `3` | Maximum number of employees one buddy can support. |
